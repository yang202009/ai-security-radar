# 检索与核验

## 检索预算

默认以信源覆盖与关键主张查清为完成条件，条数只是上限参考。

| 模式 | 第一轮 | 补缺查询参考上限 | 交付 |
|---|---|---|---|
| quick | 5 个核心入口 | 约 4 个 | 3—5 个事件，说明有限覆盖 |
| balanced | 8 个核心入口 | 约 8 个 | 5—8 个事件 |
| deep | 12 个入口，另补相关专题和框架 | 约 15 个 | 8—12 个事件或专题分析 |

除入口查询外，按范围执行最多 3 个方向查询，发现清单外原始材料。公开社区补搜默认 quick 为 0、balanced 为 2、deep 为最多 5 个平台查询；显式要求社区时 quick 可补 2 个。入口数、社区数和补缺预算分开记录。明确专题只查相关方向，`--sources` 限定入口时仍可追溯原文；用户明确“只查这些来源”则省略范围外查询。

上限不限制打开核验原文。证据依赖时有序追溯；不对同一无结果查询反复重试。第一轮入口可搜索其域名或打开专题索引，不把“索引读到了”写成“该站所有新闻已覆盖”。记录实际方式。

## 查询质量与实体核对

先把产品名、产品形态与安全问题拆开，保留准确版本和 CVE。官网及官方仓库确认实体，原始研究确认攻击术语；目标账号、仓库、社区只有在实际找到并核对后才作为定向入口，不从产品名拼出路径或 handle。

- 宽题“AI 安全”按三个方向拆查询；“Agent”“MCP”“Copilot”等多义词加产品或协议全名、厂商与安全条件。已有上下文足以确定时直接推进，仍会改变目标的歧义才提问。
- 中文主题补英文术语，海外查询保留英文专名；不因中文输入就要求配置额外搜索后端。中文入口使用中文同义词，厂商名和攻击面保持一致。
- `search_query` 用简短关键词，内部的筛选问题用完整问句。时间用独立窗口与检索筛选控制，少用“最近”“最新新闻”等占据关键词的措辞。日期筛选仍须原文复核。
- 为专题写 1—4 个安全子问题，例如目标产品的注入入口、工具权限、修复／绕过、实际利用证据。每个子问题保留实体锚点，不让泛“RCE”“jailbreak”检索淹没目标。
- 第一轮大量命中无关内容时，调整一次实体锚点或拆短查询；不能把词面命中当有效候选。助手生成的是起点，Agent 依据已读证据修订，不机械跑完全部计划。

三类主题至少各做一次有针对性的查询，除非用户限定方向：

- AI 系统：`prompt injection`、`agent security`、`MCP tool poisoning`、`RAG poisoning`、`memory poisoning`、`AI supply chain`、`sandbox escape`。
- AI 辅助攻击：`AI-assisted attack`、`adversarial misuse`、`autonomous intrusion`、`phishing`。没有技术或观测证据的“AI 驱动”不算确认。
- AI 防御：`AI vulnerability discovery`、`agentic code review`、`cyber evaluation`、`SOC automation`。优先公开方法、评测范围和报告。

英文查询服务海外入口，中文补充国内关键词。中文媒体作为发现入口时仍追溯原文，不因转载语言改变证据等级。

## 信源使用

`sources.json` 为唯一维护的机器可读信源清单。`source-review.md` 记录附件评估快照与评分方法，不作为另一份长期清单。评分是编辑判断，不能代替本次对日期、影响和修复的核验。

### 选择与去重

按预设或 `lanes` 选择入口，避免全量扫描。`core` 为常用发现／研究池，并非每次都查；`topic` 为专题补充；`background` 不默认占重点事件；`hold` 只作待核线索。信源质量高而AI相关度低的机构可以保留在背景层。访问状态来自清单核验日与当前工具，使用时重查。

`source_family` 用来提醒共同机构与利益关系，不能机械判断证据独立性。同一厂商的不同页面或媒体对同一报告的转述只算一个原始来源；同一集团不同研究团队是否独立，要检查实验、样本和材料。MITRE／ATLAS、OWASP／GenAI和AISI／NAAIMES入口已归并；多平台或多厂商的附件标签仅保留实际URL所代表的来源。

中文企业主题使用 `china` 包补官方通报、标准文件和中文线索；英文原始研究仍须追溯。明确法律义务时核对发布、效力、适用对象与版本。论文从聚合入口回具体论文、作者代码与评测；arXiv预印本、Workshop、同行评审论文及商业会议演示分开。付费产业报告仅摘要可读时只引用公开可核内容。

### 角色

- `news`：发现事件与修复进展；转述不等于独立确认。
- `research`：原始披露、审计、机制解释；检查测试条件与利益关系。
- `analysis`：解释和线索；引用技术主张时追溯其所链接的原始材料。
- `threat-intelligence`：实际观测；区分观察数据与归因推测，留意厂商可见范围。
- `context`：框架与案例库；旧知识作为背景，不冒充窗口内新闻。
- `archive`：专题历史原文；先核对当前更新情况，默认不当持续新闻流。
- `official`：官方通报、指南与政策；区分发布事实、机构观察及法律义务。
- `vulnerability`：漏洞收录或响应入口；受影响产品、修复与真实利用各自追原文。
- `academic`：论文入口；核对版本、方法、评审状态及实验边界。
- `community`：投稿与竞赛；按作者和每篇材料判断，平台身份不担保所有内容。
- `industry`：市场、产品分类与采购背景；不能用融资、排名或用户评价证明防御效果。
- `directory`：导航与检索工具；只找材料，不支持技术或事件结论。

候选事件的原始作者不在清单里时，允许跟到作者报告、产品公告、官方漏洞页和论文。对新来源检查作者身份、方法、原始材料和披露记录；本次可以引用，不自动修改长期信源清单。

当前入口 URL 和角色会随时间变化，使用时检查重定向与实际内容。访问失败可用站内限定搜索或另一可用原始披露入口，最多一次替代；仍受限就记录。仅摘要可用于线索，不能冒充已读全文或完成日期、影响范围与修复状态的核验。

### 社区与代码材料

公开社区用于发现原作者披露、维护者修复、使用条件、复现争议与企业提问。按价值优先 GitHub、Hacker News，再按主题补 Reddit、X、YouTube；不是全平台必查清单。原生数据走 [引擎协作规则](last30days-bridge.md)，网页结果不能冒充 API 返回、完整时间线或评论抓取。

GitHub 区分维护者公告、release／修复 PR、用户 issue、概念演示和 README。一个公开 issue 是报告者的主张；“closed”可能是重复或拒绝，不能单独证明修复。关联版本、维护者说明和补丁后再判断；不执行仓库代码或 PoC。

X／Reddit／HN 区分原作者披露与转载；作者身份和指向的原始材料须核对。YouTube 只有实际读取的字幕、演讲材料或带时间点的内容才能支持讲者的主张；标题、缩略图和观众评论只作线索。评论中报告的体验标为自述，不推成普遍故障。

互动数、播放量和跨平台出现次数反映可见传播，不能提高漏洞证据等级。引用评论只在它提供具体条件、争议或读者问题时使用，不强制凑引用；保留作者和该条评论的实际链接，不把主帖 URL 当评论链接。没有真实历史基线时不写“热度暴增”“攻击激增”。

## 本次覆盖状态

维护按查询／来源的运行记录：查询与时间、执行工具、返回状态、正文读取状态、原始材料及缺口。计划初始 `not-run`，未执行项保留原值；不能将预设清单或配置健康当作已覆盖。

| `search_status` | 证据含义与表述 |
|---|---|
| `ok` | 查询正常返回候选；仍需实体、日期和正文筛选 |
| `no-results` | 查询正常完成但返回零匹配；只说明该查询，不推广为平台无讨论 |
| `partial` | 只取到部分内容／页数，覆盖受限 |
| `rate-limited`／`auth-failed`／`unreachable`／`timeout`／`schema-drift`／`error` | 来源或工具失败；不能解释为安静或无新闻 |
| `skipped-unconfigured`／`not-run` | 未配置／未执行，均不计已覆盖 |

另记 `read_status`：`not-attempted`、`full-text`、`excerpt-only`、`blocked`。搜索正常不等于读到正文；搜索有候选但全部窗口外／不相关时，保留 `ok`，记录筛选后零入选及原因。日期待核、实体不符和证据弱不伪装成工具失败。

引擎结果保留原始 `Report.source_status` 或 `Partial Coverage`；引擎的 `skipped-unconfigured`、限流等不因宿主补搜而改成成功。诊断／doctor 只说明配置或缓存预测，本次运行状态才说明实际结果。统计分别记录候选链接、聚类事件、已核验入选事件，平台数和 URL 数都不等于独立证据数。

## 时间真实性

1. 保存 `published_at`、`event_at`、`updated_at` 和核验截止时间；没查到的留空／写未知，不借抓取日期补齐。
2. 日报按今天的北京时间自然日，日报中的未知小时注明仅日期已知。过去 N 天默认 N 个自然日含今天；严格滚动小时窗口遵从用户要求。
3. “窗口内新闻”要求原始披露／报道的发布时间在窗口内；老事件的新报道注明原事件时间。仅新转载没有新增事实，合并到旧事件并从重点新闻排除。
4. 老报告在窗口内有实质更新（新影响范围、修复、真实利用等）时，可以“更新”入选并提供新增内容的证据；站点自动刷新日期不算。
5. 没有日期的材料放背景或待核。结束日是今天时，禁止纳入核验截止时刻之后的内容；时区无法确定的边界事件说明不确定性。
6. 搜索结果日期、`after:`／`before:`、搜索引擎 recency、站点排序均不保证日期准确。打开页面、官方公告或论文元信息复核；日期须属于正文，不能取侧栏“最新文章”、相关链接或页脚日期。历史区间只能概括截至当时已公开的信息，后来修复状态必须另标“后续更新”。

## 事件证据表

可在临时工作记录维护下表，保留报告时附录保存；聊天无需展示全部字段。

| 字段 | 记录内容 |
|---|---|
| 事件身份 | 产品、原作者、披露名称／CVE、机制；同机制在不同产品上的独立披露可分开 |
| 关联与新增性 | 上次事件编号／链接，首次披露／实质更新／更正／重复／背景，新增主张及其证据 |
| 日期 | 原文发布、事件发生、实质更新、当前核验截止 |
| 原始证据 | 直达 URL、作者、正文读取成功与否、关键事实出处 |
| 影响范围 | 产品形态、版本／配置、涉及的用户或数据；未给出就未知 |
| 前提与能力 | 用户交互、已有权限、工具权限、是否需要特殊配置；读取／外泄／执行等实际效果 |
| 实际利用 | 研究 PoC／公开真实利用证据／来源未说明；不能仅凭 CVE 判断 |
| 修复 | 披露时状态、核验时状态、公告 URL；“缓解措施”不等同“根治漏洞类别” |
| 交叉核验 | 原报告、公告、独立复现、媒体转述；记录各自证据依赖 |
| 社区线索 | 平台、原作者／维护者／用户自述、实际帖子／评论／PR URL；与原始材料的关系 |
| 主张可信度 | 强／中／待核及简短理由，冲突与缺口 |
| 用途价值 | 企业决策、客户问答、POC 验证项、候选选题；推断单独标明 |

“成功率 80%”必须伴随样本量、条件和来源；无法核实不转成普遍成功率。“零点击”“远程代码执行”“已修复”必须有相应前提和证据。CVE 不存在也可能是有效机制研究；有 CVE 也不证明真实利用。

## 排序与综合

先通过三道入选门槛：目标实体与网络安全问题相关；有窗口内披露或可核的实质更新；关键机制／效果有可阅读原始证据。正文受限、日期不明或主张冲突的线索放待核区，不靠点赞和重复报道补足。引擎标为 `Nothing solid this window` 的相关性失败候选不支持社区结论，不能从统计数字或被拒绝的评论反推趋势；已核验的宿主原文仍可独立支持安全事件。

入选后先看证据可核验程度，再看现实影响、近期新增性、与用户用途的相关性。实际利用和已部署产品的实质修复优先阅读；研究 PoC 也可入选，说明前提。影响考虑数据敏感度、权限、暴露规模和现实条件；不把 CVSS、点赞或文章数量当完整风险判断。候选选题可按案例新意与解释价值排序，不能因此提高技术结论的置信度。

两份原文相互冲突时，不取平均：具体列出冲突的主张、测试环境和核验状态。对同一原报告的多家转载，只增加传播覆盖，不增加独立证据。

综合跨事件的变化需要至少两个独立案例支持。仅一个案例时写“这个案例提示”，不宣称行业普遍趋势。可把客户提问写成“需要确认 Agent 是否有外发权限”，不在未知客户环境里断言“必须更换平台”。

“支持工具隔离”等厂商主张只能与同一产品形态、版本、配置和威胁模型的测试比较。默认配置与特殊配置分开；一个演示失败不能证明所有部署失效。总结企业判断时写清可确认的问题及预期证据，不将未经测试的控制建议写成保证有效的修复。

## 交付前自查

- 每条重点新闻确有窗口内披露或实质更新，日期与当前核验截止时间相容。
- 每条具体事实的链接直达支持它的原文；未读到正文的主张没有冒充已核验。
- 原文、产品公告和独立复现的依赖关系正确；媒体转载已聚类。
- 同名实体已核对；方向和社区子查询保留目标，词面命中已过滤。
- 产品、版本、用户交互、权限和真实利用状态没有超出原文。
- 缓解／修复与行业级防御建议分别标明；数字有样本与条件。
- 企业影响、客户问答和选题标明推断，有事件证据可追溯。
- 报告只陈述实际覆盖；缺少信源或事件如实交代。无结果时给覆盖范围和线索，不补造新闻。
- 配置可用、查询完成、正文可读与事件入选分别记录；失败没有写成零匹配。旧报告与社区热度没有冒充近期独立证据。
- 中文表达自然、标点规范。交付完整报告时检查冗词、泛化判断和中文标点；宿主有文字审校规则时遵循该规则；简短简报做相称的清晰度自查。
